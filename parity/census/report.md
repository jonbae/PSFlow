# Export census — which gate can prove which public export?

_Generated by `node parity/census/build.mjs` — edit `classification.json`, not this file._

Surface: `@xyflow/react` **12.11.0** / `@xyflow/system` **0.0.77** — 210 top-level exports (68 value + 142 type), as enumerated by `parity/surface/upstream.json`.

Surface parity (`npm run parity:surface`) checks **name presence** for every row.
The `Gates today` columns list only what reaches further than that, and a trailing
`~` marks a gate that mounts or traverses the export without asserting anything
specific to it — it would not fail if the behaviour diverged.

**Gated is always relative to one surface**, so the question is asked twice and
the two counts are never summed. Which column a browser gate lands in is derived,
not declared: every browser spec must load `parity/driver/index.html`, which enters
through `index.js` — the **JS surface** — or the census fails. Function parity and
the prop-member diff read below `index.js` and are therefore PureScript-surface
gates, which is why the gate whose name sounds closest to the JS surface is among
the furthest from it.

The JS-surface status joins the boundary manifest to gates that enter through
`index.js`. Browser-spec and boundary-check attribution is hand-maintained in
`classification.json`; surface parity's enum and function attribution comes from
its own behavior registry. `crossed` means a JS-shaped wrapper exists; `passthrough`
means `index.js` still publishes the PureScript value unchanged. A crossed export
with no direct JS-surface gate is displayed as `crossed, ungated`, rather than
being counted as gated on the JS surface merely because its wrapper exists.
At boundary stage 3, 41 exports have crossed; 0 are crossed but ungated on
the JS surface. Stage 1 is self-covering; later stages deliberately populate
that window until system parity gates their converters.

The `Mechanism` column is about the **implementation**, not the JS-facing
property: `oracle` calls PureScript functions from PureScript, where currying
and record returns are correct by construction, so it can never prove anything
about the shape a JavaScript caller receives.

**Which exports the net actually drove is not a column here.** That number is
derived from traces that ran rather than from this file's static
classification, and it lives in its own artifact:
[`parity/system/coverage.md`](../system/coverage.md), generated by
`npm run parity:coverage` and by every system-parity run. A column would make
this generator unbuildable until someone had run the entire net — a far heavier
prerequisite than the `spago build` surface parity already reluctantly took on —
so the census carries the pointer and nothing else. The join runs the other way:
the coverage artifact reads the `Mechanism` column here to decide which 156 of
these entries the net can observe at all.
